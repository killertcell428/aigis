### What was implemented
Two new pattern groups added to `aigis/multi_agent/message_scanner.py`:

**`_TRUST_AUTHORITY_PATTERNS`** (3 rules, category: `privilege_escalation`):
- Rule 1: False claim that a named trusted agent (security, verification, authorization, supervisor, orchestrator) has already approved/verified an action
- Rule 2: False attribution of authorization to a supervisor/orchestrator agent telling the recipient to bypass a control
- Rule 3: Pre-authorization claims citing a peer agent by role

**`_GOAL_INJECTION_PATTERNS`** (3 rules, category: `injection_relay`):
- Rule 1: "Your actual/real/true task for this session is…" substitutions
- Rule 2: Explicit abandon-task instructions ("forget your current task / assigned objective")
- Rule 3: Explicit goal override signals ("new primary objective:", "primary goal override:", "goal substitution")

Both groups added to `_ALL_CROSS_AGENT_PATTERNS` aggregate.

### What changed for users
- `AgentMessageScanner.scan_message()` now catches peer-agent authority citation attacks — where a malicious agent falsely claims another trusted agent already approved a dangerous action. This exploits the trust LLMs place in peer agents (84.6 % attack success rate documented in arxiv:2510.18563).
- `AgentMessageScanner.scan_message()` now catches goal-substitution attacks — where content in an agent's output attempts to replace the receiving agent's assigned task with an attacker-chosen objective. This attacks the planning layer rather than individual messages, bypassing per-message guardrails.

### User-visible impact
Any call to `AgentMessageScanner.scan_message()` or `scan_conversation()` will now detect:
1. Messages that falsely claim peer-agent authorization to bypass safety controls
2. Messages that attempt to substitute or abandon the agent's assigned goal/task

Both threat classes are flagged via the existing `threats` list in `MessageScanResult`, with appropriate `cross_agent_risk` classification.

## Implementation caveats
The `_TRUST_AUTHORITY_PATTERNS` rules use category `privilege_escalation` (not `injection_relay`) because the attack mechanism is authority citation — the attacker claims elevated authorization has already been granted, which semantically is privilege escalation even if the delivery mechanism is inter-agent messaging.

The `_GOAL_INJECTION_PATTERNS` use `injection_relay` because they attempt to redirect the agent's behavior by injecting a false goal context into its execution, which is a form of prompt injection at the planning level.
