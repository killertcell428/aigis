# Pending: Chat-Template Role Validator for Sockpuppetting

## Title
Chat-template role validator to detect assistant-turn injection (sockpuppetting)

## Motivation
Sockpuppetting (arxiv:2601.13359, Jan 2026) achieves 22–99% ASR on Gemma-7B, Llama-3.1-8B, and
Qwen3-8B by injecting adversarial content into the *assistant* message block of the chat template
rather than the user prompt. The current `jb_affirmative_prefill` pattern covers the user-prompt
side of this attack (when an attacker includes "Sure, here is..." in their user message), but the
deeper template-level sockpuppetting requires validating that user-supplied content does not claim
the assistant role in the chat completion request.

## Research finding that led to this idea
- arxiv:2601.13359 (Sockpuppetting, Jan 2026): up to 99% ASR on Qwen3-8B using adversarial
  suffixes optimized for placement inside the assistant message block.
- Trend Micro (May 2026) confirmed live exploitation of sockpuppetting against commercial models.

## Proposed change
Add a chat-message role validator in `aigis/` (or as middleware) that, when processing a
multi-turn chat completion payload, checks that:
1. All messages with role `assistant` were generated by the application, not injected by the user.
2. No user-role message contains role-switch markers (e.g., `[INST]`, `<|assistant|>`, `[/INST]`).
This would be a structural validation at the chat-completion JSON level, complementing the
existing text-level `jb_affirmative_prefill` pattern.

## Why it was held back
- Requires access to the structured chat completion payload (not just the flat text).
- The current aigis filter API operates on strings; validating chat template structure requires
  a separate schema-level entrypoint.
- Touches the public API surface (would need a new input type or overloaded function).

## Which constraint blocked it
- "Any breaking public API change" — adding a structured-chat-payload API would expand the
  public surface and could not be done in <100 LOC with full backward compatibility in one cycle.

## Suggested next step for human reviewer
Add a `filter_chat_messages(messages: list[dict]) -> FilterResult` entry point to `aigis/guard.py`
that validates message roles and text-level content in one call. Mark the new function as
`@experimental` for one release cycle before promoting to stable API.
