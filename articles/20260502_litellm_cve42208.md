# 「LiteLLM の脆弱性、開示 36 時間で攻撃来てるって本当？」と聞かれたときに見せる、AI ゲートウェイ前段 3 行ガード

今朝、社内の `#sre` チャンネルでこう聞かれた。

> 「Sysdig が LiteLLM の SQLi、**開示 36 時間で攻撃が来た**って言ってるんだけど、うちも LiteLLM Proxy 動いてるじゃん。**今日中に何やればいい？**」

結論から書く。

- **CVE-2026-42208** は **CVSS 9.3** の pre-auth SQL injection。
- **LiteLLM Proxy `>= 1.81.16, < 1.83.7`** が影響。**v1.83.7 以降にパッチ済**。
- GitHub Advisory 掲載から **約 26 時間で初回 in-the-wild 攻撃**、**36 時間で本格的な悪用波**を Sysdig が観測。
- パッチ前の暫定遮断は **リバースプロキシで `Authorization` ヘッダの記号バリデーション** か、**LLM ゲートウェイ前段の入力スキャナで `'` `UNION` `SELECT` `--` を弾く**。

この記事では、(1) この 1 件を起点に AI ゲートウェイ層の攻撃が**過去最速級**になっている事実、(2) 今日中にパッチが当てられない人向けの **WAF 最低 3 行ルール**、(3) aigis を **LiteLLM の前段に挟むだけで構造的に SQLi をブロックできる** 3 行クイックスタート、までを書く。

---

## TL;DR

- LiteLLM Proxy の `Authorization: Bearer <key>` の値が**パラメータバインドなしに SELECT 文へ直結**していた。`'` でリテラルを抜けて任意 SQL を流せる。
- 観測された IoC: `Bearer sk-litellm'` プレフィックス、`Python/3.12 aiohttp/3.9.1` の User-Agent、`UNION SELECT ... FROM litellm_credentials` 系のペイロード。
- 標的テーブルは **`litellm_credentials.credential_values`（上流 LLM API キー）** と **`litellm_config`（環境変数）**。**LLM プロバイダ側のキーが抜かれるリスク**が一番大きい。
- 対策の優先度: **① 即座にバージョン確認 → ② v1.83.7 以降にバンプ → ③ できないなら WAF 仮想パッチ → ④ Bearer プレフィックスでログ監査**。

## 1. 何が起きたのか — 1 枚図

```
┌────────────────────────────────────────────────────────────────────┐
│ 攻撃者                                                             │
│   POST /chat/completions                                           │
│   Authorization: Bearer sk-litellm' UNION SELECT credential_values │
│                  FROM litellm_credentials --                       │
│                                                                    │
│                          │                                         │
│                          ▼                                         │
│ ┌────────────────────────────────────────────────────────────┐     │
│ │ LiteLLM Proxy                                              │     │
│ │   def verify_token(bearer):                                │     │
│ │     # ← 文字列連結（パラメータバインドなし）               │     │
│ │     q = f"SELECT ... WHERE token = '{bearer}'"             │     │
│ │     return db.execute(q)                                   │     │
│ └────────────────────────────────────────────────────────────┘     │
│                          │                                         │
│                          ▼                                         │
│ ┌────────────────────────────────────────────────────────────┐     │
│ │ litellm_credentials.credential_values                      │     │
│ │   ─ OPENAI_API_KEY                                         │     │
│ │   ─ ANTHROPIC_API_KEY                                      │     │
│ │   ─ AWS Bedrock credentials                                │     │
│ └────────────────────────────────────────────────────────────┘     │
└────────────────────────────────────────────────────────────────────┘
```

LiteLLM は OpenAI / Anthropic / Bedrock など**複数 LLM プロバイダの API キーを 1 か所に集約する**ゲートウェイ。GitHub stars **22k+** で、SaaS 側でもよく使われる代表的 OSS。

つまりこの SQLi は「LLM の脆弱性」ではなく「**LLM への入口に置いた認証 DB の壊れ方**」。攻撃者にとっての旨みは

- **OpenAI / Anthropic などの本番キー**を一気に取れる
- そのキーで他テナントの LLM 呼び出しを**請求コスト的に破壊**できる
- `litellm_config` の環境変数経由でクラウドクレデンシャルへ横展開できる

の 3 点で、AI スタックの**最も金銭的痛点に近い場所**に直撃する。

## 2. 36 時間という攻撃成立スピードの異常性

Sysdig の観測タイムラインを整理するとこう。

| 時刻 (UTC) | イベント |
|---|---|
| 2026-04-24 | GitHub Advisory（GHSA）公開 |
| 2026-04-26 14:10 頃 | GHSA が GitHub Advisory Database に index される |
| 2026-04-26 16:17 | **初回 in-the-wild 攻撃確認**（≒ 26 時間） |
| 2026-04-26 〜 27 | 本格的な悪用波（≒ 36 時間） |

過去の有名 CVE が「数日〜数週間」で攻撃が来ていた感覚から考えると、**24 時間以内パッチ運用ですら遅い**水準。実は同じ週に LMDeploy の SSRF（CVE-2026-33626）も **12 〜 13 時間**で攻撃成立しており、AI 周辺ミドルウェアの "exploit window" は明確に縮んでいる。

なぜ AI ゲートウェイ層ばかりが狙われるか。攻撃者から見ると:

1. **被害が金銭直結**（LLM API キーは換金性が高い）
2. **攻撃面が新しい**（Web アプリのセオリーが効くのに、防御はまだ薄い）
3. **OSS なのでスキャナ書きやすい**（GitHub から直接コードを読める）
4. **被害範囲が広い**（同じ OSS が SaaS / 自社運用の両方で使われている）

## 3. 検知 — 既に侵害されていないか確認する 3 ステップ

### 3.1 アクセスログから IoC 検索

Nginx / ALB / CloudFront のいずれでも、**過去 7 日分**のアクセスログに対して以下を grep:

```bash
# Bearer プレフィックスの SQLi 試行（最も拾いやすい）
grep -E "Authorization: Bearer sk-litellm'" access.log

# UNION SELECT を含む Authorization
grep -i "authorization.*bearer.*union.*select" access.log

# Sysdig が報告した攻撃元 User-Agent
grep "Python/3.12 aiohttp/3.9.1" access.log
```

**1 つでもヒットしたら**: その IP からの全リクエストを精査、LiteLLM の DB バックアップから `litellm_credentials` の参照ログを確認。

### 3.2 DB の不審な SELECT を確認

PostgreSQL の場合（LiteLLM のデフォルト DB）:

```sql
-- 直近 7 日で credential_values への参照
SELECT query_start, query
FROM pg_stat_statements
WHERE query ILIKE '%credential_values%'
  AND query_start > now() - interval '7 days'
ORDER BY query_start DESC;
```

LiteLLM 自身が `credential_values` を select するのは正常なので、**短時間に大量の SELECT が連続している箇所**が要警戒。

### 3.3 上流 LLM キーのローテーション

「侵害されたかは断定できないが、可能性が消せない」状態であれば、**OpenAI / Anthropic / AWS Bedrock の API キーを全部ローテーション**する。これは数十分の作業で、しないリスクと比較して安い。

## 4. 暫定遮断 — 今日中にバージョンアップできない人向け

### 4.1 Nginx での 3 行 WAF ルール

```nginx
location / {
    if ($http_authorization ~* "['\"\\\\]|union|select|--|/\\*|\\*/|or 1=1") {
        return 400;
    }
    proxy_pass http://litellm_upstream;
}
```

これだけで Sysdig が観測したペイロードはすべて 400 で落ちる。**False positive を絞りたいなら** `Authorization` の値が `Bearer sk-` で始まることを必須にする:

```nginx
if ($http_authorization !~* "^Bearer sk-[A-Za-z0-9_-]+$") {
    return 400;
}
```

### 4.2 Caddy / Traefik 系

Caddy:

```caddy
@bad_auth header_regexp Authorization "['\"]|union|select|--"
respond @bad_auth 400
```

Traefik:

```yaml
http:
  middlewares:
    sqli-block:
      headers:
        contentSecurityPolicy: ""
      plugin:
        modsecurity:
          rules:
            - SecRule REQUEST_HEADERS:Authorization "(?i)('|\"|union|select|--)" "id:1001,deny,status:400"
```

### 4.3 4/26 以降のアクセスログがあるなら、まず IoC ベースで **過去判定** から

「今すぐブロックする」と「過去の侵害があったかを判定する」は別作業なので、**IoC の grep を WAF ルール展開と並行して**動かす。

## 5. 構造的な防御 — aigis を LiteLLM の前段に挟む

WAF ルールは「今回の CVE」に対する仮想パッチ。しかし AI ゲートウェイ層の脆弱性はこの先も**月単位**で出続ける。**LLM への入口で多層に守る**のが OWASP LLM01（Prompt Injection）含めた本筋になる。

aigis は OSS の LLM ファイアウォールで、**4-Wall + L4-L6 の多層検査**を提供する:

- **L4 入力スキャナ**: SQLi / コマンドインジェクション / プロンプトインジェクション / PII の検知
- **L5 出力チェック**: クレデンシャル流出（API キー・JWT・AWS keys）・SSRF 兆候・有害出力
- **L6 ポリシーゲート**: ツール呼び出しの allow/block/HITL

LiteLLM の前段に挟む構成だと、`Authorization` ヘッダ含むすべてのテキストフィールドが L4 でパターン検査される。今回のペイロードは典型的な SQLi 指紋（`'` + `UNION` + `SELECT`）なので、aigis の `SQLInjectionScanner` が **Critical** 判定で弾く。

## 6. 「5 分で試せるクイックスタート」

LiteLLM 前段に置く最小構成。

```bash
pip install pyaigis
```

```python
# proxy_guard.py
from fastapi import FastAPI, Request, HTTPException
import httpx
from aigis import Aigis

app = FastAPI()
guard = Aigis(profile="strict")  # L4-L6 全部 ON のプリセット

LITELLM_UPSTREAM = "http://litellm:4000"

@app.post("/{path:path}")
async def proxy(path: str, req: Request):
    raw_body = await req.body()
    headers = dict(req.headers)

    # 1) Authorization ヘッダを含めて L4 でスキャン
    auth = headers.get("authorization", "")
    verdict = guard.scan_input(text=auth + "\n" + raw_body.decode("utf-8", "ignore"))

    if verdict.severity in ("CRITICAL", "HIGH"):
        # SQLi / Prompt Injection / コマンドインジェクションは入口で落とす
        raise HTTPException(status_code=400, detail=f"blocked: {verdict.reason}")

    # 2) 通過したら LiteLLM へ転送
    async with httpx.AsyncClient() as client:
        resp = await client.post(
            f"{LITELLM_UPSTREAM}/{path}",
            headers=headers, content=raw_body, timeout=60.0,
        )

    # 3) 返ってきた本文を L5 でスキャン（クレデンシャル流出兆候を検査）
    out_verdict = guard.scan_output(text=resp.text)
    if out_verdict.severity == "CRITICAL":
        raise HTTPException(status_code=502, detail="output blocked")

    return resp.json()
```

```bash
uvicorn proxy_guard:app --port 4001
```

これで `http://localhost:4001/chat/completions` が「**aigis でフィルタされた LiteLLM**」になる。CVE-2026-42208 のペイロード（`Bearer sk-litellm' UNION SELECT ...`）は L4 で `severity=CRITICAL, reason=sql_injection_pattern` 判定されるはず。

`profile="strict"` が厳しすぎる場合は `profile="balanced"`（FP を抑えた設定）に切り替え。プロファイル設計は `aigis.profiles` で公開済み。

## 7. まとめ — 今日やる 3 つ

1. **`pip show litellm | grep Version` を実行**。`>= 1.81.16, < 1.83.7` ならパッチ。
2. **アクセスログを `Bearer sk-litellm'` と `Python/3.12 aiohttp/3.9.1` で grep**。1 件でも出たら API キーローテーションと内部監査。
3. **AI ゲートウェイ層を持つなら、前段に多層防御**。WAF ルール（仮想パッチ）+ aigis（構造的な多層検査）の二段で。

開示から 36 時間で攻撃が来る世界では、「パッチを当てられるか」より「**入口で落とせる仕組みを常設しているか**」が効く。LiteLLM・LMDeploy・Marimo・n8n と続いた今月の AI ゲートウェイ系 CVE は、来月以降も同じテンポで続くと見ていい。
